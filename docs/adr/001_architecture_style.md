**Контекст**

Проект Typography - единая платформа для заказа полиграфии, объединяющая заказчиков и типографии. Система должна поддерживать:

- Регистрацию и аутентификацию пользователей с ролями (заказчик, работник типографии)
- Загрузку, валидацию и конвертацию файлов изображений (PNG, JPG/JPEG)
- Онлайн-редактор макетов с предпросмотром
- Подбор типографий по критериям (срок, расположение, загрузка, рейтинг)
- Оформление и сопровождение заказов с трекер-системой
- Чат между заказчиком и типографией
- Онлайн-оплату

Команда состоит из 4 человек, из которых 2 - разработчики. Технологический стек зафиксирован: Django REST Framework (бэкенд), Vue.js + Vuetify (фронтенд), PostgreSQL (СУБД), Docker (развёртывание).

Необходимо выбрать архитектурный стиль: **монолит** или **микросервисы**.

**Рассмотренные альтернативы**

| Критерий                            | Монолит              | Микросервисы                        |
| ----------------------------------- | -------------------- | ----------------------------------- |
| Сложность разработки                | Низкая               | Высокая                             |
| Скорость вывода MVP                 | Высокая              | Низкая                              |
| Порог входа для команды             | Низкий               | Высокий                             |
| Независимое масштабирование         | Ограничено           | Полное                              |
| Сложность развёртывания             | Низкая (1 контейнер) | Высокая (оркестрация)               |
| Накладные расходы на инфраструктуру | Минимальные          | Значительные                        |
| Согласованность данных              | Простая (одна БД)    | Сложная (распределённые транзакции) |

**Решение**

Выбран **монолитный архитектурный стиль** с чётким разделением на модули (apps) внутри Django-проекта:

```
text
apps/
├── accounts/    # пользователи, авторизация
├── catalog/     # категории товаров, цены, параметры печати
├── orders/      # заказы, корзина, статусы
├── printing/    # типографии, их условия и прайсы
└── api/         # Django REST Framework настройки
```

**Обоснование:**

1. **Размер команды.** 2 разработчика не могут эффективно поддерживать микросервисную инфраструктуру - это потребует дополнительных компетенций.
2. **Скорость вывода MVP.** Монолит позволяет быстрее итеративно разрабатывать и тестировать функции.
3. **Единая БД.** PostgreSQL уже выбран как СУБД; в монолите не нужно решать проблемы распределённых транзакций.
4. **Простота развёртывания.** Docker-контейнер с Django + PostgreSQL - минимальная конфигурация, которая укладывается в требования по доступности (≥ 99,5%).
5. **Возможность выделения сервисов.** При росте нагрузки можно выделить наиболее нагруженные модули (например, обработку файлов) в отдельный сервис без полной перестройки архитектуры.

**Последствия**

**Положительные:**

- Быстрая разработка и вывод MVP
- Простое развёртывание через Docker Compose
- Легко тестировать (один процесс, одна БД)

**Отрицательные:**

- Все модули масштабируются вместе - нельзя независимо увеличить мощность только обработки файлов
- При росте команды возможны конфликты в кодовой базе
- Технологический стек един для всего приложения (нельзя использовать разные языки для разных модулей)

**Меры митигации:**

- Модульная структура (apps/) с чёткими границами ответственности
- Выделение тяжёлых операций (валидация файлов, конвертация) в отдельные задачи
- Подготовка к возможному выделению сервисов: использование интерфейсов
